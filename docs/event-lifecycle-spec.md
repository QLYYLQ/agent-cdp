# agent-cdp 事件调度与生命周期更改规格

日期：2026-10-15。状态：行为需求已确认，供上游实现与验收。

实现基线：agent-cdp 0.4.0，本地提交 `70af5f0`。本次更改统一事件等待、取消与结果的含义，补齐队列和资源生命周期接口，修复 CDP session 路由与暂停 target 的恢复行为。适用对象是 agent-cdp 及其调用方；AF 的接入工作单独列出。

本规格汇总了已确认的 24 项需求。下文明确写出的默认值和行为属于约束；未固定名称的结果类型、合同类型及参数名，由上游实现时统一命名并提供类型声明，不得用任意 metadata 或私有属性代替公共合同。

## 职责边界

| agent-cdp 负责 | AF 负责 |
|---|---|
| scope 内事件调度、队列、连接和逐接收者执行状态 | 浏览器 tab 与 run 的组织、任务和动作语义 |
| 通用接收者要求、等待与结果检查接口 | 声明哪些 watchdog 处理方法必须参与，以及业务成功条件 |
| CDP bridge 按消息信封正确路由 | 解释 target、iframe、BrowserContext 和 run 的归属 |
| scope 及其桥、连接的生命周期 | 浏览器、云会话与浏览器专用 watchdog 的生命周期编排 |
| 公开诊断、统计和错误事实 | 将实际执行事实接入 AF 的观测、动作结果和 trace |

scope 是事件调度范围，不是 BrowserContext、浏览器权限或多 run 安全隔离。一个 watchdog 可以连接多个 scope；一个 scope 也可以连接多个 watchdog。同 tab 的观测 scope 向 JS scope 投递是正常协作。

AF 的轻量与完整 trace、metrics 合并、WAL 持久化策略不进入本次 agent-cdp 实现。记录器失败与实际执行隔离的要求由 AF 落实。

## 等待与执行预算

等待上限属于一次等待操作；处理器执行上限属于一次实际处理。两者独立配置，不能继续共用一个会被等待者修改的 `event_timeout`。

- 等待从调用者开始等待计时，包含这段等待期间的排队时间。
- 执行从处理器真正开始运行计时，不把之前的排队时间扣进去。
- 同一个事件的多个等待者可以使用不同等待预算，彼此不修改预算，也不改变处理器执行预算。
- `emit_and_wait` 和各结果汇总入口使用同一套等待实现，不通过修改共享事件字段设置本次等待上限。
- 等待超时与处理器执行超时明确区分。二者采用一致的诊断结构，不能一个给详细错误、另一个只抛裸 `TimeoutError`。

超时诊断逐个列出尚未完成的接收者：事件与连接身份、处理器名称、scope、排队或执行状态，以及已等待或执行的时间。已成功、失败、取消或拒收的结果仍可读取。

## 取消与串行执行

普通等待者超时或被取消，只结束自己的等待。观察者不能因为不再等待，就隐式撤销其他调用方仍在使用的事件。

提供显式的执行取消入口。事件发起方可以选择在放弃等待时撤销尚未开始的处理；AF 的动作调用采用这种选择。取消按每个接收者的一次投递处理，保留事件、连接与目标 scope 的身份。

| 接收者当前状态 | 取消请求的结果 |
|---|---|
| 尚未开始 | 结算为已取消，保证之后不再执行 |
| 已经完成 | 保留已有结果，不改写历史 |
| 正在执行 | 请求中断，等待处理器实际退出，再记录实际结果 |

取消正在执行的处理器是协作式请求。发送给 Chrome 的点击、输入和导航可能已经生效，不能报告为已回滚，也不能把“等待被取消”写成“动作一定没发生”。

同一个 scope 保持串行：前一个排队处理器实际结束之前，不启动下一个。处理器不响应取消时，明确报告它仍在运行及 scope 无法继续串行服务，不能假装它已经停止后放行下一项。

处理器自身抛出 `CancelledError`，必须留下取消结果，不能静默杀死 scope 的队列消费者。scope 自身关闭或消费者任务被外部取消属于另外的生命周期事件，不能用统一吞掉 `CancelledError` 的方式处理。

## 接收者合同与业务结果

agent-cdp 提供正式公共接口，让调用方声明每条“事件到处理方法”连接的参与方式，并为请求声明必需接收者、完成要求和业务结果规则。声明粒度是连接与请求，不是给整个 watchdog 类统一贴一个成功标签。

库负责记录实际发生的派发和执行事实。调用方负责业务含义。例如 AF 的导航请求中，权限检查通过只表示允许导航，日志监听收到事件只表示观察到了请求；实际导航处理者的结果才说明导航执行情况。

合同必须支持以下行为：

- 普通通知允许无人订阅。明确要求处理的请求，在缺少实际必需接收者时失败。
- 必需接收者检查基于过滤后实际适用的连接；被过滤掉的连接不算接收者。
- 观察连接，包括日志与 `expect()` 临时监听，不能填补实际执行接收者的缺失。
- 接收者要求在执行副作用前检查。需要多个必需结果时，缺少其中一项不能冒充完成。
- 等待结束表示所等待的参与者已结算，不自动表示业务成功。成功检查与读取部分结果有明确公共入口。
- 返回 `None`、返回业务对象或返回含错误信息的结构，其业务含义由显式结果合同决定。库不能猜类名、字典键或返回值的真假。
- 逐接收者保留成功、失败、执行超时、未开始即取消、运行中取消和队列拒收的事实。一个接收者成功不能掩盖另一个必需接收者失败。
- 业务错误、取消和诊断均保留原始原因及归属，不只留一条汇总字符串。

沿用现有连接身份、事件类型、过滤器和结果记录机制；新增的参与及结果合同必须出现在公开类型/API 中。具体 wrapper 或角色枚举名称不在本规格中强制指定。AF 可以通过明确的结果校验或转换规则使用自己的业务结果类型。

## 队列容量与拒收

`EventScope` 和 `ScopeGroup.create_scope` 都公开队列容量配置。`queue_maxsize` 默认保持 1024，0 表示无界；AF 的浏览器归档 scope 使用 65536。

`emit` 保持不阻塞。队列满时：

- 拒收计数可查询，能够区分事件类型及接收者。
- 被拒收的投递有明确结果和 `QueueFullError`，不能仅打一条日志再假装正常完成。
- 事件可显式声明不可丢；这类事件遇到队列满，`emit` 当场同步报错。
- 一个事件有多个接收者时，分别记录谁已接收、谁被拒收。不承诺多个 scope 的派发具有原子回滚能力。
- 拒收数量、原因和归属必须保留。合并重复警告是实现建议，可以汇总数量、时间范围和类型，避免每丢一件刷一条相同警告。

如以后需要等待队列空位的发送方式，使用独立的显式接口，不改变 `emit` 的含义。本次必需交付的是上述非阻塞发送与可见拒收。

## 公开配置与统计

容量、历史保留和慢处理警告设置通过正式参数传入。附加元数据单独通过 `metadata={...}` 传入；未知关键字直接报错，不能静默收进 metadata。`create_scope` 与直接创建 `EventScope` 的配置能力一致。

慢处理警告的阈值和检查间隔可按 scope 配置、可关闭，消息带 scope 身份。慢处理警告与确定的同 scope 自等待检测相互独立：关闭前者不能关闭后者。

公开只读统计至少包括当前排队数、队列峰值、接收/处理完成/失败/取消/拒收数量，以及排队等待和处理器执行耗时。一次事件投递给多个接收者时，以逐接收者投递为统计口径；事件数量与投递数量不能混为一个数。统计不能依赖访问 `_event_loop._queue` 或替换内部方法。

本次提供稳定查询接口，不要求另建一套观察钩子系统，也不为了统计额外保留所有事件内容。

## 原生排空屏障

提供类似 `scope.flush(timeout=...)` 的原生排空接口。调用时固定一个已接收投递的前缀，等待该前缀全部结算；失败、取消等终态也算结算。

- 屏障本身不占队列位置，不会因队列满而被拒收。
- 调用后新来的投递不延长这次等待，持续输入不能使屏障永远等不到结束。
- 排空成功不等于所有业务处理成功；调用方可以检查该前缀的结果和失败信息。
- 已拒收的投递必须在诊断中可见，不能把仍在排队的任务误计为已经丢失。
- 超时报告尚未结算的接收者，采用统一超时诊断。
- 在当前 scope 的处理器里等待包含自身的屏障，按确定的自等待拒绝，不能等到超时。

AF 归档收集可以用这个入口替代当前“向队尾投递一个空事件”的自制屏障。

## 关闭与资源所有权

公开两种关闭方式：等待已有任务收尾，或请求立即关闭。等待收尾的预算可配置，默认保留 10 秒；空闲 scope 不再等待 0.5 秒轮询后才退出。

关闭顺序是停止新输入，停止桥继续向该 scope 送事件，再按所选策略处理已有任务，最后断开对应连接并释放资源。

- 等待收尾：让已接收任务在关闭预算内完成；到期后请求取消剩余工作。
- 请求立即关闭：撤销未开始的投递，请求取消正在运行的处理器。
- 到关闭预算结束时，处理器仍未实际退出，返回或报告未关完，不继续无限等待，也不承诺强制终止 Python 协程。保留监督和后续清理所需的任务引用，不能清空对象表后假装资源已经释放。
- `ScopeGroup.close_all` 并行尝试关闭全部 scope，不能因一个失败跳过其他 scope。
- 已记录的处理器业务异常不在 close 时重新冒充清理异常。真正的清理失败在全部尝试后汇总。
- 关闭和解绑操作幂等。已手动关闭桥，再关闭 scope，应正常完成。
- scope 关闭只解除它拥有或承接的绑定。共享 watchdog 在其他 scope 上的绑定继续有效；同一事件在其他 scope 的投递不被顺带取消。

`WatchdogProtocol` 补齐正式的按绑定解绑能力，与 attach 对称。具体 tab 的两组 scope、共享 watchdog 的浏览器拓扑和浏览器会话关闭仍由 AF 编排；不能用关闭整个 watchdog 代替解除某一个 scope 的绑定。

桥与 scope 的生命周期联动。桥的事件工厂或投递失败应留下可见诊断，不能让异常逃入 CDP 收包循环而中断其他消息处理，也不能静默丢掉拒收事实。

## 事件历史与引用释放

`max_history_size=0` 表示一条事件历史也不保留，修复 `[-0:]` 导致全保留的问题。默认历史数量仍为 1000。说明历史保留的是事件对象及其关联内容，数量限制不等于字节限制。

处理器完成后，取消的超时计时器、上下文变量和内部执行结构不应继续无谓持有事件与大结果，直到原始超时时间到点。清理不破坏调用方仍持有的结果，也不提前删除明确配置保留的历史。

## 接线校验与自等待

在 `connect` 和相关接线入口提前拒绝能够确定的 handler 与 DIRECT/QUEUED 模式不匹配。不能等标签页真正崩溃时才发现异步崩溃处理器被挂到同步直接模式。

保留执行时对实际返回值的校验，覆盖装配时无法确定的动态可调用对象；不通过无声包装把错误配置改成另一种执行语义。

同 scope 的队列处理器等待需要该 scope 自己继续消费才能完成的事件，立即报错，并指出可改用 `target_scope` 或调整调用结构。保持一个 scope 一次处理一项的保证，不引入队列重入。

## CDP session 路由与工厂参数

绑定 session 的 `CDPEventBridge` 只按消息信封上的路由 session 匹配。缺少可信路由 session 的消息不能默认匹配；不能用 `params.sessionId` 回退冒充路由。

例如 `Target.attachedToTarget` 的信封 session 可能表示父会话，而 `params.sessionId` 表示新附加的子会话。两者必须分别保留。浏览器级事件由明确的浏览器级订阅处理，AF 再解释 target 和子 session 归属。

事件工厂保留只接收 `params` 的入口；显式启用 `with_session=True` 时，收到 `(params, route_session_id)`。不通过猜测函数签名自动切换传参方式。路由信息在浏览器级事件上可以为空；绑定 session 的 bridge 已在调用工厂之前完成匹配检查。

未绑定 session 的 bridge 保留“没有 session 过滤”的含义，可以接收带路由 session 或不带路由 session 的已订阅消息；不能把它同时解释为“只接收无 session 的消息”。AF 如需进一步区分浏览器级消息与特定 target 的消息，使用明确传入的路由信息和自身分派规则，不能靠缺失信息回退。

过滤规则不建立共享 Chrome 的访问权限。bridge 路由修复不能替代 AF 的 BrowserContext、target、recorder 和 run 所有权设计。

## 暂停 target 的恢复

`CDPCommandProtocol.send` 增加可选 timeout 参数；未传时沿用客户端既有默认，不额外覆盖其超时策略。`PausedTarget` 的恢复操作有独立、可配置的等待预算，默认 5 秒；内建 CDP 恢复和自定义恢复函数都使用此预算。

恢复调用将 `session_id` 作为 CDP 路由参数发送，不能塞进命令 params。成功收到恢复应答后才标记已恢复。

- 发送失败、超时或取消时，不得标成恢复成功。
- 失败后允许调用方明确再次尝试；成功之后再次恢复是幂等操作。
- 并发恢复不能重复发送，也不能在另一次恢复尚未成功时提前报告成功。
- 等待预算到期后请求取消并报告恢复未确认，不承诺强制终止自定义协程或撤回已发送的 CDP 命令。原尝试未实际退出之前，不得启动新的恢复尝试；仍在运行的尝试保持可跟踪。
- 不自动无限重试。
- 主体操作成功、恢复失败时，明确报告恢复失败。
- 主体操作已失败、恢复也失败时，保留主体异常并附上恢复失败。恢复期间新到来的外部取消仍须传播，不能被更早的普通主体异常吞掉；取消也不能被普通清理错误覆盖。

文档和测试应准确描述旧错误：命令落到了浏览器级而没有恢复目标，不是恢复了另一个 target。现有断言错误路由写法的测试必须重写。

## 立即布防的事件等待

`expect` 在创建 waiter 的当下注册监听，返回可等待、可关闭的对象。调用方先注册，再触发导航等操作，不需要靠调度一次协程来争取监听先安装。

- 超时从注册监听开始计算，不从第一次 await 开始。
- waiter 支持上下文管理，异常退出或未继续等待时也能解绑。
- 匹配完成、超时、取消、主动关闭及所属 scope 关闭，均释放对应监听。
- waiter 属于观察者，不满足执行请求的必需处理者要求。
- 取消 waiter 只停止该监听，不撤销事件实际执行。

AF 可以替换目前为避免注册过晚而手写的事件等待逻辑。

## 诊断日志与依赖

零命中默认只记录 DEBUG。单个订阅显式设置 `expect_hits=True` 时，结束后没有命中才发 WARNING；例如正常运行中未出现崩溃或弹窗，不再产生警告噪音。保留公开的命中计数查询。

修正 `event_result` 中与实际情况相反的错误文字。所有结果聚合入口遵守本规格统一的等待、诊断与业务结果合同。

把实际在运行时使用的 `anyio` 声明为运行时依赖，不能依赖 AF 的模型 SDK 间接安装它。构建产物必须能在只有声明依赖的干净环境里导入并使用基础能力。

## 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 同一事件被两个调用方用不同超时等待 | 一个等待超时不影响另一个，也不改变处理器预算 |
| 动作排在慢任务后，发起方放弃并撤销未开始工作 | 动作之后不执行，有明确取消结果 |
| 已运行的处理器收到取消请求 | 记录请求和实际结束结果；不声称 Chrome 副作用被回滚 |
| 处理器忽略取消 | 不启动同 scope 下一项，不报告已停止或已完整关闭 |
| 一个处理器自行取消，scope 仍有其他任务 | 取消结果可见，消费者继续处理后续任务 |
| 没有实际执行者，只有日志或 expect 监听 | 必须处理的请求被拒绝；普通通知按合同允许无人处理 |
| 处理器返回 None 或业务错误结构 | 按显式合同解释，不按 truthy 或任意字典键猜测 |
| 多个接收者中只有一部分成功或被队列拒收 | 逐接收者结果完整，必需接收者失败不被成功项掩盖 |
| 队列容量通过两个公开入口设置 | 实际容量一致生效；默认 1024，0 无界 |
| 容量等参数拼写错误 | 当场报错，不进入 metadata |
| 队列满且事件声明不可丢 | emit 同步报错，已投递和拒收的部分均可查询 |
| 队列已满时 flush，且不断有新事件到达 | 屏障不被丢，只等待调用时前缀；等待中的项目不被算作丢失 |
| flush 前缀内有业务失败或取消 | 能排空并读取这些结果，不声称全部成功 |
| 处理器在自己 scope 内自等待，包括等待含自身的屏障 | 立即给出有定位信息的错误 |
| 关闭多个 scope，其中一个清理失败 | 所有 scope 都被尝试关闭，真正清理失败最后汇总 |
| 关闭共享 watchdog 的一个 scope | 对应绑定释放，其他 scope 继续正常工作 |
| scope 已关闭，Chrome 又发来原订阅消息 | 桥已解绑，不向关闭的 scope 投递，不破坏收包循环 |
| 历史设为 0，大结果处理完成后释放用户引用 | 无历史残留，计时器不无谓延长大结果生命周期 |
| 能确定的 DIRECT 与异步处理器不匹配 | 接线时拒绝；动态形状仍有执行时保护 |
| bridge 绑定 session A，信封为 B 或缺失，而 params.sessionId 为 A | 均不被错误路由到 A |
| attachedToTarget 的父路由与子 session 不同 | 工厂正确取得两种信息，匹配只看信封路由 |
| PausedTarget 恢复成功、发送失败、5 秒超时及再次尝试 | 成功才置位；失败可显式重试；成功后重复调用幂等 |
| 主体异常与恢复异常同时发生 | 主体原因保留，恢复失败可见；取消不被普通错误替换 |
| 创建 expect 后立即触发事件，尚未 await waiter | 仍能收到事件；退出后无残留监听 |
| 普通零命中与声明 expect_hits 的零命中 | 分别按 DEBUG 与 WARNING 处理 |
| 干净环境只安装构建包及声明依赖 | import 与基础事件功能正常，不依靠开发依赖 |

单测覆盖调度、取消、队列、过滤与资源回收；假 CDP 客户端覆盖路由和失败路径。暂停 target 的内建恢复需要真实 Chrome 验收，证明正确路由真正使目标继续运行。上游现有测试、lint、类型检查和构建检查全部通过后，再进行 AF 接入验收。

## AF 配套更改

当前分工：agent-cdp 由用户在上游实现，AF 接入尚未开始。接续条件是上游改动已完成，并有可供 AF 安装或引用的明确版本/提交。届时先核对实际公开接口与本规格，再更新 AF 的依赖下限和锁文件，完成以下配套与验收。需求文档完成不等于上游已实现，也不等于 AF 已采用。

- 创建归档 scope 时设置容量 65536；加运行时/测试断言，防止旧版本把参数吞进 metadata。
- 为事件与 watchdog 连接声明参与及结果合同；动作不再把空结果或监听成功当成执行成功。
- 动作发起方采用已定的等待、排队撤销及运行取消语义；保留实际错误和不确定副作用的信息。
- 接入原生 flush，删除被替代的空事件屏障；统一使用上游公开拒收与排队统计。
- 接入 scope/桥/按绑定解绑生命周期，验证 tab 关闭不影响共享 watchdog 服务其他 tab。
- 修正 AF 自己的 CrashWatchdog 接线与 target 身份处理；上游的接线校验用于提前暴露错误，不能代替 AF 修配置。
- 更新暂停 target 金丝雀测试、相关路由措辞和可以复用新 expect 的等待代码。
- 选择合适的 tab 历史保留量，验证 DOM 与截图不会被无意保留整个长 run。
- 跑 AF 的相关单测与真实 Chrome 录制、观测、动作和回放验收，确认没有错误的跨 tab 路由或清理影响。

以下 AF 议题继续单列：多 run 共享 Chrome 的 BrowserContext/target/recorder 所有权、给 watchdog 的 CDP 访问边界、统一 trace/metrics 及 WAL 隔离、全框架私有成员与公共 API 审查。现有 JS 同 tab/OOPIF 归属校验保留；不因本次 scope 改动一刀切禁止正常跨 scope 协作。
